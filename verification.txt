Frontend: Implement the Evidence and Quality Review UI
Objective
Build an investigator-facing Evidence and Quality Review interface for
reviewing extraction warnings, contradictions, provenance, and aggregated
evidence sets.

The screen must allow an investigator to trace an extracted finding back to
the source record and safely record a review decision without modifying or
hiding the original extraction result.

Reference design
Image
User story
As an investigator, I want to review warnings and contradictions and inspect
their supporting evidence so that I can assess extraction quality, understand
uncertain findings, and leave an auditable review decision.

Primary route
/cases/:caseId/evidence-review
The selected review item should be addressable in the URL.

Example:

/cases/case_001/evidence-review?type=warning&id=warning_001
Scope
The page should combine:

A review queue for warnings, contradictions, and evidence sets.
A protected source-record viewer with evidence-span highlighting.
A provenance and extraction-quality panel.
Review actions, notes, and audit history.
This interface reviews extraction output. It does not rerun extraction,
perform entity resolution, or modify source evidence.

Proposed API integration
Method	Endpoint	Purpose
GET	/api/v1/cases/{caseId}/evidence-review-items	Load the paginated review queue.
GET	/api/v1/evidence-review-items/{reviewItemId}	Load a selected warning, contradiction, or evidence-set review item.
GET	/api/v1/entity-extractions/{extractionId}/warnings	Load extraction warnings.
GET	/api/v1/entity-extractions/{extractionId}/contradictions	Load extraction contradictions.
GET	/api/v1/entity-extractions/{extractionId}/evidence-sets/{evidenceSetId}	Load an evidence set and its record references.
GET	/api/v1/evidence-records/{recordId}	Load source-record metadata.
POST	/api/v1/evidence-records/{recordId}/reveal	Request protected source content and create an audit event.
POST	/api/v1/evidence-review-items/{reviewItemId}/actions	Start, complete, defer, or reopen a review.
GET	/api/v1/evidence-review-items/{reviewItemId}/notes	Load investigator notes.
POST	/api/v1/evidence-review-items/{reviewItemId}/notes	Add an investigator note.
GET	/api/v1/evidence-review-items/{reviewItemId}/audit-events	Load the item's audit trail.

12. Standard API errors
Use application/problem+json for errors:

{
  "type": "https://api.example.test/problems/evidence-access-denied",
  "title": "Evidence access denied",
  "status": 403,
  "detail": "You do not have permission to reveal this evidence record.",
  "instance": "/api/v1/evidence-records/message_001/reveal",
  "code": "EVIDENCE_ACCESS_DENIED",
  "traceId": "trace_7d21"
}
Expected status handling:

Status	Frontend behavior
400 Bad Request	Show a validation message without clearing loaded data.
401 Unauthorized	Invoke the application's authentication flow.
403 Forbidden	Keep protected content hidden and show an access-denied state.
404 Not Found	Show that the item or source record is unavailable.
409 Conflict	Reload current review state and explain the concurrent update.
410 Gone	Clear expired revealed content and offer a new deliberate reveal action.
422 Unprocessable Content	Show the backend's safe validation message.
429 Too Many Requests	Respect Retry-After; do not retry reveal actions automatically.
500 Internal Server Error	Preserve loaded metadata and offer a manual retry.

State synchronization
Selecting a queue item loads its source record and provenance.
Selecting a related temporary ID opens the Extraction Result Explorer.
Selecting an evidence-set record updates the source viewer.
The active category, filters, and selected item should be reflected in the
URL where practical.
Updating review status should update both the queue item and summary counts.
Navigating between records must not discard an unsaved note without warning.
Security and privacy requirements
Enforce case and evidence authorization through the backend.
Do not persist evidence content in local storage, IndexedDB, or service-worker
caches.
Do not include sensitive content in URLs, analytics, error reports, or
console logs.
Sanitize and render extracted text as plain text.
Prevent browser autocomplete in sensitive note or evidence fields when
appropriate.
Clear protected content after its access window expires.
Audit every protected-content reveal.
Respect server cache-control headers.
Do not expose unauthorized cross-case references.
Accessibility requirements
Review tabs and queue items must be keyboard accessible.
Evidence highlights must include a non-color indicator.
Severity must use text and iconography, not color alone.
Screen readers must announce selection and review-status changes.
Focus must move predictably when the selected queue item changes.
The protected-content reveal action must explain its effect.
Non-functional requirements
Virtualize large review queues.
Cancel outdated detail requests when selection changes rapidly.
Keep the queue usable while item details are loading.
Preserve previously loaded metadata if protected-content retrieval fails.
Use server-provided timestamps and display the active timezone.
Prevent duplicate review actions while a request is in progress.
Acceptance criteria

The investigator can view warnings, contradictions, and evidence sets.

Review items can be searched, filtered, sorted, and paginated.

The sample AMBIGUOUS_PERSON warning renders correctly.

Related temporary IDs link to the Extraction Result Explorer.

Provenance displays the correct file and record IDs.

Valid source offsets highlight the exact evidence span.

Invalid offsets produce a visible warning rather than incorrect highlighting.

Evidence-set ranges and explicit record lists are supported.

Protected content is hidden until deliberately revealed.

Protected-content reveals generate an audit event.

The investigator can start, complete, defer, and reopen a review.

Review actions preserve the original extraction result.

Concurrent review updates are handled without silently overwriting state.

Investigator notes can be added and viewed.

Audit events are visible and read-only.

Empty, loading, missing-record, forbidden, and API-error states are implemented.

No evidence content is written to persistent browser storage or logs.

Unit and end-to-end tests cover the principal review workflows.

Objective
Build an investigator-facing Entity Resolution Review interface for
reviewing potential identity matches across files and devices.

The screen must explain why two extracted records may represent the same
canonical entity, allow an authorized investigator to accept, reject, or defer
the candidate, and preserve an auditable and reversible decision history.

Reference design
Image
User story
As an investigator, I want to compare a pair of extracted entities and inspect
the evidence and scoring behind a proposed match so that I can make an
informed, reversible resolution decision.

Primary route
/cases/:caseId/resolution
The selected candidate should be addressable in the URL.

/cases/case_001/resolution?candidateId=candidate_001
Scope
The page should combine:

A resolution-candidate queue.
Side-by-side source-entity comparison.
Resolution confidence and weighted match rationale.
Supporting source records and provenance.
Canonical entity preview.
Accept, reject, and defer actions.
Merge and decision history.
The frontend displays backend-generated resolution candidates and scores. It
must not calculate the authoritative resolution score in the browser.

High	>= 0.85	Prioritize for review; never auto-accept in the UI.

Low	< 0.60	Show as weak evidence; rejection may be likely but remains a human decision.

7. Resolution actions
Provide:

Start review
Accept match
Reject match
Defer
Reopen
Accepting a match means the two records represent the same canonical entity.
Rejecting means they represent different entities. Deferring records no

Number of records and relationships affected
Reversibility notice
Any conflicts that will remain attached to the canonical entity
Before Reject match, allow an optional reason and make clear that the
decision may suppress the same candidate from being regenerated.

Every action must:

Use an idempotency key.
Include the candidate's expected version.
Be authorized by the backend.
Produce an audit event.
Preserve the original extracted entities.
8. Reversible decisions
The UI must state that resolution decisions are reversible.

For accepted matches, provide access to:

Reversal should be a separate, permission-controlled workflow. Do not place a
one-click destructive-looking undo control in the candidate comparison panel.

Reviewer

Previous and new state
History is read-only and must not be editable or deletable from the frontend.

10. Warnings and contradictions
Show warnings when:

The same identifier is associated with different people.
Strong attributes conflict.
Evidence timestamps are inconsistent.
The match relies mainly on weak or shared identifiers.
One source record is unavailable.
Accepting the match affects existing relationships.
Contradictions must remain visible after a match is accepted. Acceptance must
not imply that conflicting evidence was deleted.

Use application/problem+json:

Status	Frontend behavior
400 Bad Request	Show validation errors without clearing loaded comparison data.
401 Unauthorized	Invoke the application's authentication flow.
403 Forbidden	Hide protected data and show an access-denied state.
404 Not Found	Show that the candidate or source record is unavailable.
409 Conflict	Reload the candidate and explain the concurrent decision.
410 Gone	Show that the candidate was retired or superseded.
422 Unprocessable Content	Show the backend's safe decision-validation message.
429 Too Many Requests	Respect Retry-After; do not retry decision actions automatically.
500 Internal Server Error	Preserve loaded comparison data and offer a manual retry.

Frontend: Implement the Entity Extraction Jobs UI
Objective
Build an investigator-facing Entity Extraction Jobs page for starting,
monitoring, filtering, retrying, and opening entity-and-relationship extraction
jobs for a case.

The page must support incremental processing. When a new file is added to a
case, previously completed and unchanged files should be reused rather than
extracted again.

Incremental extraction rule
Before creating jobs, the backend should classify each eligible case file as:

NEW: no extraction exists.
CHANGED: the current file hash differs from the completed extraction.
OUTDATED: schema, extractor, model, or definition version requires a new
extraction.
FAILED: the latest compatible attempt failed and may be retried.
PROCESSING: a compatible extraction is already running.
REUSABLE: an unchanged compatible completed result already exists.
INELIGIBLE: no extractable content or unsupported file type.
The frontend must display this classification before submission. It must not
decide independently whether an existing result is reusable.

Example:

Day 1: File 1 → completed extraction
Day 2: File 2 uploaded

Day 2 extraction preview:
File 1 → REUSABLE, skipped
File 2 → NEW, queued
